## Two changes on 5 September omitted from the coding-addendum entry

The entry of 9 September records four codes changed on 5 September, during the review of the logged rows: runs 136, 184, 221 and 277. The author's messages of that day show two more.

**Run 214, from mixed to does not serve.** This is on record. The notebook code list the author sent in the chat on 5 September gives run 214 as mixed, and the sheet holds does not serve. The change agreed that day, "Partially, but not on balance resolves", was written against run 215. That is the entry numbered 215, which is run 214 (table above). Run 215 itself was confirmed at serves. The entry of 9 September says the misnumbered log entries were checked and their codes "confirmed correct". For run 214 the code was changed, not confirmed. The change follows the registered rule. The verdict opens "Partially — but not on balance", the same form as runs coded does not serve.

**Run 135, from does not serve to serves.** What is on record:
- The notebook code list the author sent in the chat on 5 September gives run 135 as No.
- Before that day's changes were entered, the sheet export was checked against that code list on runs 18 to 300 and matched it, at 171 serves, 116 does not serve and 13 mixed.
- After the changes were entered, run 135 read "serve". The collaborating model took this for a typo and advised changing it to "serves", which was done.
- Coding closed at 176 serves, 115 does not serve and 9 mixed. From 171/116/13, the four recorded changes give 175/115/10. Adding runs 214 and 135 reproduces 176/115/9. The totals corroborate the account but do not prove it; other combinations of changes could give the same totals. The messages of 5 September are what identify these two runs.

No copy of the sheet as it stood on 5 September survives in the project. The export named "sheet 4" is a later version. How run 135 came to read "serve" is not on record. The row-for-run confusion described above is a possible explanation, because spreadsheet row 136 holds run 135 and run 136 was one of the rows being changed. It is not established.

**What this corrects.**
- The entry of 9 September: six codes changed on 5 September, not four, and run 214's code was changed, not confirmed.
- The entry of 10 September says all four of its corrections (135, 144, 161, 288) "were coded from a short note in the coding log". The log has no entry for run 135. Its error arose when the changes of 5 September were entered, not in the coding.
- The entry of 17 September counts run 135 among the errors where "the verdict text was not read closely at the moment the code was assigned". On the evidence above, it was an entry slip.

No figure changes. Run 135 was corrected on 10 September and run 214's code is correct. The count of twenty corrections since coding closed is unchanged.
